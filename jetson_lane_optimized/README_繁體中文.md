# Jetson Nano 抓線優化版 v2

主程式：`jetson_car.py`。這次只修改 Jetson；ESP32 不用重燒，仍使用你原本的 `CTRL`、`MANUAL` 指令、115200 baud、正值左轉／負值右轉。原始兩份程式保存在 `original/`。

## 截圖中的問題

原程式 `ROI_TOP=0.02`，幾乎整張圖都參與抓線，家具和牆邊也會進入搜尋。左右兩區各自挑黑色群組，起始點先選最寬的群組，容易從錯誤物體開始追蹤。左右搜尋區還在 x=145～175 重疊。

`MIN_VALID_PAIRS=5` 實際上只檢查左右各有 5 點，沒有確認這些點是同一批高度上的有效配對，也沒有檢查離群點、垂直涵蓋範圍和擬合誤差。截圖左側剛好 L:5，右側 R:21；左線很少的點也被拿去做普通直線擬合，再上下延伸 60 像素。

因此，畫面上長長的藍線不代表真的看到這麼長的線。截圖足以指出此風險，但已疊上的文字、黃點和藍線會污染影像，無法還原當時原始候選點或確定每個誤抓來源。

## 新版改了什麼

- 只分析畫面高度 22%～92% 的地面；Otsu 門檻也只從此區域計算。
- 使用 ROI Otsu 與局部亮度對比；遠處淡線即使比 Otsu 門檻亮，也能以周圍地面的對比納入。仍排除低對比大片陰影。保留細線，避免原本 3×3 opening 把細膠帶消掉。
- 全寬收集候選點，使用有上限、固定抽樣的 RANSAC 直線候選與離群點剔除；每個掃描高度只算一票。
- 至少 7 點、涵蓋 28 像素高度，並檢查點的連續性；先配對再選控制高度，左右共同可見範圍至少 24 像素。控制高度限制在共同觀測範圍內，附近必須真的有點。依照你的要求保留自動延伸：觀測範圍畫青色實線，上下各最多延伸 60 像素畫藍色虛線。虛線是预测，不當成額外偵測點。
- 左右線成對檢查：不可交叉、車道寬度合理、近處比遠處寬、共享足夠的可見高度。多組近似同分的車道判定為模糊。
- 前後影格的左右邊界若在控制高度跳動超過 24 像素，暫不採用；失線 0.45 秒後清除舊追蹤，允許重新定位。
- AUTO 連續收到 3 個不同時間的有效偵測才前進。失線直接送停止；不再沿用舊方向盲走。影像超過 0.30 秒未更新也停止。
- PD 平滑與轉向變化限制依時間計算，降低幀率不同造成的手感變化。
- 馬達指令統一由單一執行緒每 0.05 秒發送；模式切換和寫入共用鎖。串口重連後回到 MANUAL STOP，需重新選 AUTO。
- STOP 在 AUTO 也有效；手動按住才持續送瀏覽器心跳，心跳停止 0.60 秒即停止。旧手動請求不會在 STOP 後重新啟動。
- 影像最多每秒編碼 15 次，多個網頁共用同一份 JPEG；預設不開 OpenCV 視窗，適合 SSH 操作。

影像門檻和形態學運算參考 [OpenCV thresholding](https://docs.opencv.org/4.13.0/d7/d4d/tutorial_py_thresholding.html) 與 [OpenCV morphology](https://docs.opencv.org/4.12.0/d3/dbe/tutorial_opening_closing_hats.html)。此處使用基本 CPU 運算，不需要 CUDA、神經網路或下載模型。

## 在 Jetson 上執行

1. 將 `jetson_car.py` 複製到 Jetson 的工作資料夾。先停止原本正在執行的控制程式，避免兩個程式同時搶攝影機和串口。
2. 沿用原本能執行的 OpenCV、NumPy、Flask、pyserial 環境。不要為了此版任意升級 JetPack 內建 OpenCV。缺套件才安裝：

   ```bash
   sudo apt-get install python3-opencv python3-numpy python3-flask python3-serial
   ```

3. 執行：

   ```bash
   python3 jetson_car.py --port /dev/ttyUSB0
   ```

   串口若是 `/dev/ttyACM0` 就替換該路徑。省略 `--port` 時，只有偵測到唯一相符裝置才會自動連接。

4. 瀏覽器開啟 `http://Jetson的IP:5000`，原本的 `172.20.10.4:5000` 只有在 Jetson IP 沒變時才適用。等狀態顯示 ESP32 已連線，再操作。
5. 先在 MANUAL 靜止狀態檢查抓線與「黑線遮罩」。確認後先架空車輪測試 STOP 和轉向符號，再放地測試 AUTO。

有桌面環境且想看本機視窗：

```bash
python3 jetson_car.py --port /dev/ttyUSB0 --display
```

## 調參順序

參數集中在 `jetson_car.py` 開頭。先確認影像，再調控制，不要直接加大 KP 掩蓋誤抓。

| 參數 | 預設 | 何時調整 |
|---|---:|---|
| `ROI_TOP` | 0.22 | 應保留遠處左線；若背景過多可小幅提高，但過高會把短左線裁掉 |
| `TARGET_Y_RATIO` | 0.58 | 偏好的控制高度；若一邊提早出畫面，自動移至兩線共同可見範圍 |
| `BLACK_MAX` | 125 | 黑膠帶在遮罩中消失且灰階偏亮時，小幅提高；地面也變白則降低 |
| `MIN_LOCAL_CONTRAST` | 14 | 膠帶對比不足可稍降；陰影邊緣過多可稍升 |
| `MAX_LINE_WIDTH` | 30 px | 膠帶在 320×240 影像中較粗時才提高；也需讓黑帽 kernel 寬度大於膠帶寬度 |
| `MIN_Y_SPAN` | 28 px | 太短的線段不可信；先調相機讓線段可見，不要一開始就降低 |
| `TRACK_MAX_JUMP` | 24 px | 較快移動或幀率低時可能誤判跳動；先檢查錄影和實際幀率 |
| `EXTENSION_LIMIT` | 60 px | 顯示用自動延伸長度；不會放寬控制採信條件 |

你提供的截圖中，真正的左膠帶似乎在較遠的位置便離開畫面左邊界，原本的 y=0.58 控制位置可能沒有左線證據。v1 曾因此顯示 LOST；v2 會將控制高度往上移至兩線共同可見範圍。若此範圍仍不足才停止。先確認車子位於兩線中間且鏡頭朝正前方，再調俯角與高度。不要只為讓畫面出現藍線而放寬檢查。

本版以平地、淺色地面、兩條深色膠帶和局部近似直線為假設。急彎、岔路、大片遮擋或只剩單邊線時可能停車；沒有加入未經標定的單邊推算，也沒有宣稱適用所有賽道。

## 你提出的雙輪 PI 架構

判斷：值得作為下一步，但依你「未量測，先保留我的設定」的要求，本次不更動 ESP32，也不虛構目標 RPM 與 PI 增益。保留原本的腳位、143／147 脈衝設定、左右基準 PWM 115／110、kick PWM 135／130 與 kick 150 ms；並未套用你構想中相同 PWM／0.2 秒 kick。

目前已採用 Jetson 端的車道中心 → OFFSET → PD steering → 依 steering 選 speed 流程。D 項依 OFFSET 變化率提前收回修正；原始控制定義是 OFFSET 正值代表車道中心在畫面右邊，此時 steering 負值要求右轉。若說的是「車子偏到車道右側」則 OFFSET 為負，才應左轉。

後續在確認 A 相 RISING 每輪脈衝數與實測 RPM 後，可把 ESP32 升級成左右輪獨立 PI：由速度設定共同 RPM，轉向造成左右目標 RPM 差；各輪用目標減實測 RPM 調整 PWM，配合積分限幅、停止時清零，以及非阻塞 kick。輪距、輪徑和實測速度資料會決定是否能使用物理單位。

短暫失線先減速並保持方向約 0.6 秒，是可考慮的策略，但目前原韌體的低速命令被最低 PWM 夾住，無法確認減速有效，因此本次仍採失線停止。等 RPM 閉迴路有實測後，再加入有明確時間上限的失線緩行，不能用畫面延伸的虛線持續刷新「有看到線」的時間。

## 原始錄影與離線測試

要提供調參素材，可在 MANUAL 下錄下原始畫面（包含直線、轉彎和容易誤抓的位置）：

```bash
python3 jetson_car.py --port /dev/ttyUSB0 --record raw_lane.avi
```

按 Ctrl+C 結束並封存影片。錄影是縮至 320×240、未疊文字的畫面；容器播放速度固定 30 fps，若相機實際較慢，播放時間不等於實際時間。錄影會增加 I/O，平常不用可省略。

離線處理不會開啟串口、馬達或網頁：

```bash
python3 jetson_car.py --image raw_frame.jpg --output lane_debug.jpg
python3 jetson_car.py --video raw_lane.avi --output lane_review.avi
```

單張測試另輸出 `lane_debug.jpg.mask.png`；影片輸出疊圖結果，終端顯示有效幀數。有效比例只是偵測接受率，不代表正確率，需要比對實際線位置。

## 驗證與限制

執行 `python3 -m unittest -v test_jetson_car` 可重現離線測試。已在 Windows／Python 3.12／OpenCV 4.10.0／NumPy 2.5.4 通過 16 項合成影像與控制政策測試；程式另通過 Python 3.6 語法檢查。尚未在你的 Nano／JetPack、攝影機和車體實測，語法檢查不等於完整 Python 3.6 執行驗證，也不代表 Nano 能達到 30 fps。

失線、影像逾時的「停止」指 Jetson 發出零速度指令，不代表機械煞停時間。原 ESP32 還有 150 ms 的阻塞式起步 kick、1 秒通訊 watchdog，這次依要求沒有改 ESP32。

另有一個值得後續處理的速度問題：原 ESP32 用 `speed/0.30` 比例換算 PWM，再限制最低左100／右95；因此 AUTO 的 0.24、0.21、0.18 在套用轉向和同步修正之前，基準 PWM 都會卡在同一個最低值。網頁顯示的速度是命令比例，不是實測 m/s；單改 Jetson 的速度數字，無法保證實際減速。這也是新版失線直接送 0 的原因之一。


## v2：修正低視角、左線提早出畫面的失線

你的第二張截圖在 v1 重跑為 LOST。原因包括左線較淡、左線在固定控制高度前便離開畫面，以及短線擬合被背景候選擠掉。v2 同時修正上述條件，而不是只降低有效點數。

以該截圖縮至 320×240 測試，v2 配對得到左11點、右42點，控制高度自動選 y=97，OFFSET 約 -74。這表示圖上的車道中心在鏡頭中心左側，不等於相機安裝偏移的量測。截图可能經過裁切，且已有標記，不能拿此數據取代原始攝影機實測。程式沒有為此截圖硬編碼線座標或特殊遮罩。

畫面底部顯示 `v2 P:... M:... TH:...`：P 是候選點數，M 是通過連續性檢查的線模型數，TH 是 Otsu 門檻。橘點表示候選點，黃點表示最終配對採用的點，青色實線表示擬合，藍色虛線表示自動延伸。上方 Y 顯示當前控制高度。控制高度跳動時清除 D 項的舊變化率，避免把觀測距離改變誤當車子突然橫移。

鏡頭很低且接近平視會讓遠處線細、背景多，也可能讓近處兩側線提早出畫面；但這不是從單張圖就能確定的唯一成因。先將車置於車道中央、鏡頭朝正前方，再稍微向下俯以減少背景。若近處仍無法同時容納兩線，再增加高度；不要盲目往下壓，俯角與高度需一起看取景結果。
